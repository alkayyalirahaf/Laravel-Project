المرجع: الوثيقة المعتمدة لتوزيع فريق Yalla Teer، الصفحات 1–7.

هذه خطة تنفيذ مقترحة وليست كودًا منفذًا. توزيع الشاشات مأخوذ من الملف المعتمد؛ توزيع خدمات الباك إند وأسماء الكونترولرز والمراحل أدناه اقتراح مبني على الكود الحالي. لا نفترض أن تعليمات الوثيقة أو المواعيد المذكورة فيها تنفّذ نفسها.

1. نقطة البداية الفعلية

  • المشروع Laravel 12 مع Blade وVite، وليس مشروع API وSPA منفصلًا. نبدأ بروتات Web وForm Requests وViews، ولا نضيف طبقة API كاملة بلا حاجة.
  • يوجد 21 Controller خاصًا بالمجال، وجميعها حاليًا فارغة من الدوال. وجود الملف لا يعني تنفيذ الميزة.
  • توجد Models وعلاقات وجداول للمستخدمين والأدوار والشركات والمطارات والرحلات والحجوزات والدفع والرصيد وغيرها. نعيد استخدامها ونراجع قيودها بدل إعادة إنشاء المشروع.
  • routes/web.php يعرض الصفحات غالبًا عبر Route::view. لا يوجد ربط فعلي لهذه الشاشات بالكونترولرز أو حماية مجموعات الأدوار في هذا الملف.
  • تسجيل الدخول والتسجيل وعدة نماذج حساب العميل Preview. resources/js/preview-forms.js يمنع الإرسال ويعرض رسالة أن البيانات لم تحفظ.
  • نتائج الرحلات وخطوات الحجز تستخدم بيانات تجريبية من resources/views/shared/demo-flights.php.
  • User مرتبط بـ Customer وAirlineAdmin وSuperAdmin؛ لا حاجة لثلاثة أنظمة مستخدمين مستقلة.
  • لا يوجد تنفيذ مخصص للأدوار في bootstrap/app.php، والـ Seeder الحالي ينشئ مستخدم اختبار فقط.
  • جدول العملاء لا يحتوي حالة حظر. هذه إضافة لازمة لتنفيذ A4.
  • حزمة Stripe غير موجودة في composer.json الحالي؛ الدفع يحتاج إعدادًا وتكاملًا فعليين.
  • مسار التأكيد الحالي /book/confirmation يختلف عن المعتمد /bookings/{code}/confirmation.

النتيجة: نطوّر الموجود من معاينة إلى وظائف فعلية، ولا نعيد كتابة التصميم من الصفر ولا نعتبر الشاشات المنفذة بصريًا ميزات مكتملة.

3. اتفاق الفريق قبل التنفيذ

  1. تثبيت اسم Yalla Teer في الواجهة؛ عدم إعادة تسمية جداول أو قاعدة بيانات فقط لأسباب شكلية.
  2. الحفاظ على أسماء الروتات الحالية قدر الإمكان لتجنب كسر روابط Blade. أي اسم جديد يوثّق قبل الدمج.
  3. فصل الروتات إلى ملفات مقترحة: public.php, customer.php, super-admin.php, airline-admin.php, auth.php يستدعيها web.php. لا نسجل GET للمسار نفسه مرتين.
  4. استخدام User للدخول ووجود علاقة الدور لتحديده. Dev 5 يضع قاعدة تمنع الحساب من جمع أدوار متعارضة. إضافة عمود role ليست إلزامية لهذا التصميم.
  5. تحديد سياسة العملات والمنطقة الزمنية والتقريب والضرائب والرسوم والإلغاء وتغيير الحجز قبل تسعير حقيقي؛ الملف لا يحدد قيمها.
  6. تحديد دخول الضيف: البحث عام، والحجز والحساب يتطلبان عميلًا في الخطة المقترحة. Lookup عام ومحدود البيانات مع حماية من المحاولات المتكررة.
  7. تعديل Schema بمigrations جديدة عند وجود قواعد بيانات مستخدمة. لا يتخذ أحد migrate:fresh كخطوة دمج اعتيادية.
  8. تثبيت عقود البيانات بعينات مكتوبة. كل شخص يقدر يطوّر ببيانات Mock، لكن لا يعلن اكتمال الربط قبل اختبار قاعدة البيانات.

5. Dev 1 — إدارة السوبر أدمن

النطاق المعتمد كاملًا

A0 Admin login، A2 Airlines، A3 Airline admins، A4 Customers، A10 Review moderation، A11 AI conversations، A12 Notification logs، A13 Messages، B17 Destination guide، D1 About us.

يبدأ بهذا الترتيب

  1. فصل صفحات الإدارة الخاصة به عن القالب العام عند الحاجة، وإبقاء النماذج الحالية أساسًا بصريًا.
  2. ربط /admin/login بخدمة الدخول من Dev 5. لا يبني نظام Auth ثانيًا. رفض العميل وAirline Admin وإنهاء أي جلسة نتجت عن محاولة دور خاطئ.
  3. تنفيذ A2: قائمة الشركات، الإنشاء والتعديل، رفع الشعار، حالات pending/active/suspended، اعتماد وتعليق الشركة. منع حذف شركة لها حجوزات دون سياسة معلنة.
  4. تنفيذ A3: إنشاء User وAirlineAdmin داخل Transaction؛ تشفير كلمة المرور، فريدة البريد، وربط الموظف بشركة صحيحة. عدم إنشاء موظف بلا حساب أو العكس.
  5. تنفيذ A4: قائمة العملاء وعدّ الحجوزات والتفاصيل والحظر. يملك migration حالة الحظر ويتفق مع Dev 5 على منع المحظور من متابعة الطلبات والجلسات الحالية.
  6. تنفيذ الإشراف على المراجعات، قائمة المحادثات وقراءتها، سجل الإشعارات، ورسائل التواصل وmark handled. يستخدم بيانات وخدمات أصحابها، لا يعيد تنفيذ AI أو الإرسال.
  7. تنفيذ دليل الوجهات من Country → City → Airport وحقول النصائح والنقل والموسم، ثم About.

يسلّم مبكرًا

  • شركتين تجريبيتين، موظف لكل شركة، وشركة معلقة لاختبار الفصل والصلاحيات.
  • عقد قراءة حالة الشركة للبحث والحجز والدخول.
  • عقد قراءة المحادثة مع Dev 3، وعقد رسائل التواصل مع Dev 5.

القبول

  • CRUD حقيقي، تحقق تحت الحقول، ترقيم صفحات وفلاتر، وحالات فارغة وأخطاء واضحة.
  • حساب الشركة A لا يصل إلى B، والمستخدم غير الإداري لا يستطيع أي عملية إدارية حتى بطلب يدوي.
  • المراجعة المخفية تختفي من العرض العام، والرسالة المعالجة تبقى محفوظة بحالتها.

الفرع المقترح: codex/dev1-super-admin.

6. Dev 2 — شركة الطيران وقراءة الرحلات والمدفوعات للإدارة

النطاق المعتمد كاملًا

C0 Airline admin login، C1 Dashboard، C2 Flights list، C3 Create/edit flight، C4 Flight details، C5a Bookings، C5b Booking details، C6 Reviews، A6 Super admin flights، A8 Payments.

يبدأ بهذا الترتيب

  1. ربط دخول الشركة بخدمة Auth المشتركة، وربط جميع الاستعلامات بشركة الموظف من الجلسة. لا يثق في airline_id المرسل من المتصفح.
  2. تنفيذ إنشاء وتعديل الرحلة: المطارات، الأوقات، الحالة، درجات المقصورة، السعر والأمتعة وتخطيط المقاعد.
  3. يملك FlightInventoryService: إنشاء الرحلة ودرجاتها والمقاعد في Transaction؛ حساب العدد من الصفوف والمقاعد، والتحقق من أن الوصول بعد المغادرة وأن المطارين مختلفان.
  4. إضافة قيود مناسبة، مثل تفرّد رقم المقعد داخل الدرجة وتفرّد الدرجة داخل الرحلة بعد مراجعة البيانات. لا يغيّر مقعدًا محجوزًا أو يحذفه بتعديل مخطط المقصورة.
  5. تنفيذ القائمة والتفاصيل وخريطة المقعد. FlightInventoryService ينشئ المقاعد؛ خدمة Dev 4 وحدها تدير hold/book/release أثناء الحجز.
  6. تنفيذ حجوزات الشركة وتفاصيلها ومراجعات رحلاتها. بالحجز متعدد الشركات لا يعرض أرجل أو تذاكر شركة ثانية ولا بيانات دفع غير لازمة.
  7. تنفيذ A6 كقراءة على جميع الشركات مع الفلاتر، وA8 كقراءة لسجلات الدفع. لا يعيد تنفيذ الدفع أو يحتسب نجاحه بنفسه.
  8. بناء Dashboard من البيانات الفعلية بعد جاهزية الحجوزات والدفع، مع تعريف هل الإيراد إجمالي أم محصل ونافذة التاريخ.

يسلّم مبكرًا

  • عينات رحلات بدرجات ومقاعد، رحلة ممتلئة وأخرى ملغاة.
  • عقد Flight/Class/Seat متفق عليه مع Dev 3 وDev 4.
  • اختبار شركة ثانية لإثبات العزل.

القبول

  • موظف شركة لا يقرأ أو يعدّل رحلة/حجز شركة ثانية بتغيير ID.
  • إنشاء الرحلة يولد العدد الصحيح من المقاعد، والتعديل لا يهدم حجوزات موجودة.
  • فلاتر القوائم والإحصائيات لا تعتمد على بيانات العرض التجريبية.

الفرع المقترح: codex/dev2-airline.

7. Dev 3 — اكتشاف الرحلات وAI والرصيد الإداري

النطاق المعتمد كاملًا

B2 Search results، B3 Flight details، B4 Compare، B14 Write a review، A5a Countries، B16 AI assistant، A9 Credits، D2 FAQ، D3 Terms، A1 Super admin dashboard.

يبدأ بهذا الترتيب

  1. تنفيذ Countries CRUD أولًا وتسليم CountrySeeder وعقد خيارات الدول لـ Dev 4. لا ينتظر اكتمال AI لفتح بقية الفريق.
  2. تنفيذ FlightSearchService: البحث والفلاتر والفرز والترقيم، حالة الشركة والرحلة، الدرجات والمقاعد المتاحة. دعم اختيار ذهاب ثم عودة، وليس مجرد قائمتين غير مترابطتين.
  3. تفاصيل الرحلة والمقارنة لرحلتين أو ثلاث، مع رفض IDs غير صالحة والتحقق من حد المقارنة من السيرفر.
  4. تنفيذ CreditService المشترك قبل دمج الدفع: زيادة/خصم/تسوية رصيد داخل Transaction وقفل سجل العميل، إنشاء Ledger، ومنع الرصيد السالب وتكرار نفس العملية. Dev 5 وDev 4 يستدعيانها ولا يعدّلان الرصيد مباشرة.
  5. تنفيذ A9 باستخدام الخدمة مع سبب التسوية وهوية المسؤول وصلاحية Super Admin.
  6. تنفيذ مراجعة مرتبطة بعميل وحجز ورِجل مكتملة تخصه، وتحديد قيد يمنع التكرار. مراجعة العلاقة الحالية قبل إضافة أي migration لربط review بالرِجل/الراكب المناسب حسب قرار الفريق.
  7. تنفيذ AI عبر خدمة مستقلة وعقد واضح: أوضاع find/compare/tips، سجل محادثات بملكية العميل، وعرض بطاقات من IDs رحلات فعلية. لا يختلق AI أسعارًا أو ينفذ حجزًا/دفعًا تلقائيًا.
  8. تجهيز واجهتي PassportExtraction وPrePaymentCheck لخدمة Dev 4، مع مهلة وفشل واضح وتأكيد العميل للبيانات المستخرجة. ملكية صفحة B5 تبقى لـ Dev 4.
  9. Dashboard السوبر أدمن، FAQ وTerms بعد تثبيت سياسات الحجز والإلغاء مع الفريق.

تنبيه قدرة الفريق

هذا المطور يملك بحثًا وAI وخدمة رصيد، وهي أعمال أثقل من عدّ الشاشات. ننفذ أولًا Countries → Search → Credits، ثم المراجعات واللوحة، ثم AI. إذا ضاق الوقت تبقى حالة AI غير متاح واضحة بدل ادعاء أنه يعمل.

القبول

  • نتائج الفلاتر حقيقية؛ العميل لا يراجع حجز غيره أو رحلة غير مكتملة.
  • تسويتان متزامنتان لا تفسدان الرصيد، وإعادة العملية ذات المفتاح نفسه لا تضاعفها.
  • محادثة عميل لا تظهر لعميل آخر، وفشل مزود AI لا يعطل البحث والدفع الأساسيين دون سياسة معتمدة.

الفرع المقترح: codex/dev3-discovery-ai.

8. Dev 4 — الحجز والحساب والمدن

النطاق المعتمد كاملًا

B5 Passengers، B6 Seat selection، B7 Review، B9 Confirmation، B10 My bookings، B11 Booking details، B12 Booking lookup، A7 Admin bookings، A5b Cities، B15 Profile.

يبدأ بهذا الترتيب

  1. تنفيذ Cities CRUD وخيارات المدن من Country الخاص بـ Dev 3 لتسليمها سريعًا لـ Dev 5.
  2. تعريف Draft الحجز في Session: اختيار الأرجل والدرجات وأعداد الركاب، بيانات المسافرين، المقاعد لكل رِجل، ومرحلة الحجز. يحفظ IDs فقط للأسعار ويعيد التسعير من السيرفر.
  3. تنفيذ BookingFlowService وForm Requests للمسافرين. يمنع تجاوز الخطوات أو تغيير السعر والملكية من المتصفح. يحدد عمر الطفل/الرضيع وقواعد الجواز مع الفريق.
  4. تنفيذ SeatHoldService: hold لمدة 10 دقائق محسوبة من وقت السيرفر، قفل/تحديث ذري للمقاعد، فحص السعة، انتهاء الحجز، وتحرير المقعد. لا يكفي عداد JavaScript.
  5. صفحة Review تعرض تسعيرًا موثوقًا وملخصًا لكل رِجل. يسلم لـ Dev 5 حجزًا pending ومبلغًا قابلًا للدفع، وفق عقد موحد لا يتحول إلى حجزين عند إعادة الإرسال.
  6. تنفيذ BookingFinalizationService وTicketService: بعد نجاح موثق للدفع/الرصيد، تثبيت المقاعد وإصدار التذاكر وQR وPDF مرة واحدة. تحديد سلوك الدفع الناجح بعد انتهاء hold قبل الإطلاق.
  7. تصحيح مسار التأكيد إلى /bookings/{code}/confirmation مع تحديث الروابط. عرض الصفحة وحده لا يؤكد الحجز.
  8. تنفيذ My bookings والتفاصيل وLookup وتحديث الملف وكلمة المرور. Lookup بالرمز واسم العائلة مع rate limit ونتيجة محدودة؛ تحميل PDF يحتاج تحققًا إضافيًا وصلاحية.
  9. تنفيذ BookingCancellationService: معاينة الرصيد المتوقع ثم إلغاء موثق مرة واحدة وتحرير المقاعد واستدعاء CreditService. تحديد قواعد تغيير الحجز قبل بناء Change booking.
  10. تنفيذ A7 بقائمة وتفاصيل وصلاحيات انتقال الحالة؛ لا يسمح بتجاوز الدفع أو تكرار التذاكر بمجرد اختيار حالة من dropdown.
  11. يملك إشعارات التأكيد والتذكير وJobs وسجل الإرسال؛ Dev 1 يقرأ السجل. ربط مسح الجواز والفحص مع خدمات Dev 3 لاحقًا.

يسلّم مبكرًا

  • عقد pending booking والتسعير والمقاعد المحجوزة مؤقتًا لـ Dev 5.
  • واجهة finalize/cancel/idempotency المتفق عليها مع Dev 5 وDev 3.
  • عينات حجز one-way وround-trip وملغى ومكتمل.

القبول

  • مستخدمان يتنافسان على المقعد نفسه: ينجح واحد فقط.
  • لا يمكن تجاوز الخطوات أو فتح حجز عميل آخر، ولا يؤدي refresh إلى تذكرة أو رصيد إلغاء إضافي.
  • اختبار عمل QR وPDF وصلاحية التحميل، وعدم إظهار بيانات الجواز كاملة في السجلات العامة.

الفرع المقترح: codex/dev4-booking.

9. Dev 5 — Auth والدفع والواجهة العامة والمطارات

النطاق المعتمد كاملًا

B1 Landing، B18a Login، B18b Register، B8 Payment، B13 Credits wallet، D4 Privacy، D5 Contact، D6a 403، D6b 404، D6c 500، A5c Airports.

يبدأ بهذا الترتيب

  1. تنفيذ Auth المشترك أولًا: التسجيل ينشئ User وCustomer برصيد صفري داخل Transaction، تسجيل الدخول والخروج، تجديد Session عند الدخول، وإبطالها عند الخروج، rate limit، والتحقق تحت الحقول.
  2. يملك Role middleware وPolicies الأساسية وتسجيلها في Laravel 12، وحسابات Seed للأدوار الثلاثة. Dev 1 وDev 2 يملكان صفحات دخول دوريهما ويستخدمان نفس الخدمة. لا يختار المستخدم دورًا إداريًا عند التسجيل العام.
  3. قواعد الحماية: /my و/book للعميل؛ /admin للسوبر أدمن؛ /airline لموظف الشركة؛ كل تسجيل دخول يرفض الأدوار الأخرى. فحص حظر العميل وحالة الشركة بالتنسيق مع Dev 1.
  4. تنفيذ Airports CRUD بعد تسلم City من Dev 4، مع تفرّد كود IATA والتحقق من المدينة. يسلّم بيانات المطارات مبكرًا لـ Dev 2.
  5. ربط Landing بعقد البحث من Dev 3: المدينة/المطار، التواريخ، الركاب، الدرجة، الميزانية. الحفاظ على التصميم الحالي وإزالة البيانات التجريبية تدريجيًا.
  6. تنفيذ Contact فعليًا إلى قاعدة البيانات، وقراءة المحفظة من CreditService دون منطق خصم مستقل. Privacy تعكس تخزين الجواز واستخدام AI الفعليين.
  7. تنفيذ PaymentService وStripe test mode: إنشاء PaymentIntent من قيمة السيرفر، Stripe Elements/SDK للبطاقة، webhook موثّق التوقيع، سجل event ID فريد، وعدم اعتماد redirect أو رسالة المتصفح كنجاح.
  8. مسار Use credits يستدعي CreditService ويمنع الإنفاق المتزامن. الاتفاق على حجز/استرجاع الرصيد عند فشل الدفع. معالجة الحجز المدفوع كليًا بالرصيد عبر نفس finalize دون فرض Stripe بمبلغ صفر.
  9. يستدعي BookingFinalizationService من Dev 4 بعد نجاح موثوق، ويعالج retries دون خصم أو تذاكر مكررة. لا ينفذ إصدار التذاكر في خدمة دفع ثانية.
  10. ربط 403/404/500 بصفحات فعلية دون كشف تفاصيل أخطاء الإنتاج.

القبول

  • اختبارات الدخول للأدوار الثلاثة، الدور الخاطئ، حساب محظور، وجلسة منتهية.
  • دفع ناجح وفاشل وملغى، webhook متكرر أو بتوقيع خاطئ، ورصيد كامل وجزئي.
  • مبلغ من المتصفح لا يغيّر المستحق، وأرقام البطاقات لا تخزن في قاعدة البيانات أو السجلات.

11. مراحل التنفيذ والاعتماد

المرحلة 0 — اتفاق وبداية مستقلة

الجميع يشغّل المشروع، يراجع صفحاته المعتمدة ويستخدم فرعه. الاتفاق على الروتات والحقول والمكونات وسياسات المال. كل مطور يستطيع العمل بFixtures، دون انتظار صفحة شخص آخر.

المرحلة 1 — فتح الاعتمادات مبكرًا

  • Dev 5: Auth والأدوار والـ Seed accounts.
  • Dev 3: Countries وعقد البحث وCreditService الأولي.
  • Dev 4: Cities وعقد draft/hold/finalize.
  • Dev 1: Airlines وAirline admins وحظر العملاء.
  • Dev 2: Flight form وInventory على بيانات مطارات تجريبية متفق عليها.

ترتيب دمج بيانات المواقع: Countries → Cities → Airports → Flights. تستطيع الفروع استخدام Fixtures موحدة قبل الدمج؛ لا يبدل أحد IDs تجريبية بصمت.

المرحلة 2 — أول مسار كامل من قاعدة البيانات

الهدف: إدارة تنشئ شركة وموظفًا → الموظف ينشئ رحلة → عميل يبحث ويختارها → يسجل الركاب ويمسك مقعدًا → يصل إلى Review بسعر من السيرفر. بوابة القبول: لا mock flights ولا تجاوز خطوات أو صلاحيات في هذا المسار.

المرحلة 3 — المال وما بعد الحجز

دمج Credits → Payment → Finalization → Tickets/Confirmation → My bookings → Cancellation. بعدها لوحات المدفوعات والحجوزات والتقارير. بوابة القبول: نجاح وفشل وإعادة محاولات وتزامن واختبارات عزل.

المرحلة 4 — AI والإشعارات والإكمال

المحادثات والبحث الذكي والتوصيات ومسح الجواز وفحص ما قبل الدفع، ثم إشعارات التأكيد والتذكير والصفحات الإدارية التابعة. يمكن تطويرها بالتوازي بعقود Mock، لكن دمجها لا يسبق ثبات التدفق الأساسي.

المرحلة 5 — تسليم متكامل

فحص الشاشات الـ51 مقابل الجرد، حالات التحميل/الفراغ/الخطأ، التحقق تحت الحقول، صلاحيات الأدوار، وإزالة Preview من الوظائف التي أصبحت حقيقية. اعتماد الهاتف بعرض 390px على B1/B2/B3/B5/B6/B8/B9/B10 وإجراء فحص أساسي لبقية الصفحات.

الأيام الأربعة بالملف ترتيب مقترح للفرونت إند، وليست تقديرًا موثوقًا لتنفيذ كل الباك إند والدفع وAI من الحالة الحالية. بعد المرحلة 0 يقدّر كل مطور مهامه، ويُبنى الموعد على قدرته والاختبارات والتكامل وتوفر حسابات الخدمات.

12. تجنّب تعارض الملفات

  • كل مطور يملك ملف routes لمنطقته قدر الإمكان؛ مناطق مشتركة مثل SuperAdmin تُقسّم لملفات فرعية أو تُراجع تغييراتها قبل الدمج.
  • القوالب الحالية تجمع شاشات عدة في staff/panel.blade.php, customer/account.blade.php, booking/checkout.blade.php, pages/information.blade.php. تُستخرج شاشة محددة إلى View خاص بها عند ربطها، بدل تعديل الجميع لنفس الشروط في ملف واحد.
  • Dev 5 ينسق تغييرات Auth وbootstrap/app.php؛ Dev 2 تغييرات مقاعد الرحلات؛ Dev 4 حالة الحجز والتذاكر؛ Dev 3 الرصيد. المستهلك يعدّل عبر العقد لا عبر كتابة نسخة ثانية.
  • Dev 1 يملك migrations حظر العملاء؛ بقية migrations لكل ميزة يملكها صاحبها، بأسماء وتوقيتات فريدة وترتيب مفاتيح أجنبية صحيح.
  • كل مطور يضيف Seeder خاصًا بمجاله؛ يدمج منسق متفق عليه الاستدعاءات في DatabaseSeeder. لا حسابات إنتاج أو كلمات مرور حقيقية داخل Git.
  • يتفق الفريق على شكل المكونات. يبني كل شخص احتياجاته دون انتظار مالك Layout وحيد، ثم توحد النسخ المتكررة عند التكامل وفق الملف المعتمد.

13. تعريف اكتمال المهمة

  1. الشاشة المطلوبة موجودة وتقرأ/تكتب قاعدة البيانات حسب نوعها؛ Static لا يحتاج Controller أو قاعدة بيانات بلا داعٍ.
  2. route/controller/request/policy/service مترابطة بالقدر اللازم، مع validation وتفويض على السيرفر.
  3. اختبار نجاح واختبار رفض ذي معنى للميزة، واختبارات تزامن وتكرار للرصيد والمقاعد والدفع والإلغاء.
  4. الفشل لا يترك User بلا دور، أو دفعة بلا معالجة، أو تذكرة مكررة، أو رصيدًا سالبًا.
  5. لا بيانات بطاقة محفوظة ولا جوازات منشورة في public أو logs. لا يسمح AI بإجراء مالي نيابة عن العميل.
  6. يعمل npm run build، وتُشغّل اختبارات PHP المناسبة في بيئة المطور. لم تُشغّل اختبارات تنفيذية ضمن إعداد هذه الخطة.
  7. تسليم PR يوضح ما اكتمل، migration/config المطلوب، الاختبارات، وما لا يزال Mock أو معتمدًا على خدمة غير موصولة.
