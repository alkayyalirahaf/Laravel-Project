# مراجعة دمج Yalla Teer

تاريخ المراجعة: 20 نوفمبر 2026، بتوقيت عمّان.

المراجعة شملت ملفات PHP والقوالب والروتات والاعتمادات وخدمات الدخول والبحث
والمخزون والدفع، إضافةً إلى فحوص آلية وقراءة أعداد السجلات في قاعدة التطوير.
هذه ليست شهادة اكتمال أو اختبار قبول كامل للمنصة.

تحديث بعد موافقة المستخدم على تعديل الروتات: أضيفت الروتات الناقصة مباشرة في
routes/web.php، وأزيلت تعريفات المعاينة المتعارضة والتعريفات المتكررة، وفُعلت
حماية الأدوار. نواقص ربط الروتات المذكورة في المراجعة الأصلية أُغلقت؛ النواقص
الوظيفية للحجز والرصيد والمزود والبيانات بقيت كما هي.

## الإصلاحات المنفذة

1. تنفيذ `AdminAuthController::showLogin/login` بدل الروتات المرتبطة بدوال مفقودة،
   باستخدام `LoginRequest` و`AuthService` الحاليين. أضيف حد لمحاولات دخول الأدمن
   داخل الكنترولر لأن ملف الروتات محمي. لم يُنشأ حساب أدمن أو تُمنح صلاحيات لمستخدم.
2. استخدام خدمة الدخول المشتركة لموظف الشركة، مع تطبيع البريد وفحص الدور الوحيد
   ودعم remember. لا توجد نسخة مستقلة من منطق التحقق من كلمة المرور داخل الكنترولر.
3. رفض دور موظف شركة غير نشطة من `AuthService::resolveRole`. هذا الفحص يفيد
   أيضًا الروتات التي تستخدم middleware الدور عند إعادة فحص صلاحية مستخدم مسجل.
4. توحيد `one-way/round-trip` مع `one_way/round_trip` في البحث، ودعم أسماء الفرز
   القديمة `earliest/latest`. يحسب البحث البالغين والشباب والأطفال بدل افتراض مقعد واحد،
   ويتحقق من الحدود ومن تعارض `passengers` الصريح مع مجموع الفئات.
5. طلب الرضّع يُرفض برسالة واضحة إلى حين اعتماد سياسة المقاعد. لم تُفترض سياسة
   رضيع بلا مقعد أو تسعيرة للرضيع. البحث متعدد المدن غير منفذ ولا يتحول بصمت لبحث آخر.
6. حماية قوالب الدخول والتسجيل والتواصل والـlayout من أخطاء 500 عندما تغيب
   روتات الإرسال أو الخروج. يظهر عدم توفر الخدمة؛ هذا ليس بديلًا عن دمج الروتات.
7. تثبيت الاعتمادات من `composer.lock` بواسطة `composer install --no-scripts`.
   تم تثبيت Stripe SDK الناقص ومطابقة الاعتمادات الموجودة لإصدارات القفل، بما فيها
   إعادة سبع حزم إلى الإصدارات المحددة فيه. لم يُعدّل composer.json أو composer.lock.
8. توثيق الروتات في `routes/omar-routes.txt`، ثم دمجها فعليًا في `routes/web.php`
   بعد الإذن الصريح. ملف TXT لم يُستورد؛ يبقى مرجعًا فقط. حُفظت أسماء الروتات
   وأضيفت حماية مجموعات العميل والأدمن وموظفي الشركة بالأدوار.

## وحدات ما زالت فارغة أو معاينة

- Dev 1: إدارة الشركات وموظفيها والعملاء، الإشراف على المراجعات والمحادثات،
  قراءة رسائل التواصل والإشعارات، وصفحات الوجهات الفعلية.
- Dev 2: كنترولرز ولوحات الرحلات والحجوزات والمراجعات والمدفوعات. خدمة المخزون
  موجودة لكنها لا تكفي وحدها لتشغيل الشاشات.
- Dev 4: Cities CRUD، تدفق الحجز، حجز المقاعد المؤقت، الحجوزات والتفاصيل والبحث
  عنها، الملف الشخصي، التذاكر والإلغاء والإشعارات. الخدمات النهائية المقابلة غير موجودة.
- Dev 3: منطق البحث والدول والمقارنة والمراجعات ولوحة الإدارة موجود، لكن الأرصدة
  متوقفة بأمان، والـAI وتكاملاته غير موصولة. لا تُحسب هذه الأجزاء مكتملة.
- Dev 5: كود التسجيل والدخول والمطارات والتواصل والمحفظة والدفع وروتاتها موجودة
  الآن؛ الاختبار الكامل ما زال يعتمد على تدفق الحجز والبيانات وخدمات التثبيت والرصيد.

## حالة قاعدة التطوير عند الفحص

تمت قراءة الأعداد فقط، بدون عرض كلمات مرور أو بيانات المستخدمين وبدون كتابة سجلات:

| الجدول | عدد السجلات |
| --- | ---: |
| users | 1 |
| super_admins | 0 |
| customers | 0 |
| countries / cities / airports | 0 لكل جدول |
| airlines / flights / flight_classes / seats | 0 لكل جدول |
| bookings / payments / credit_transactions / reviews | 0 لكل جدول |

الحساب الموجود وحده لا يكفي لتجربة الأدوار. يلزم إعداد حسابات AuthSeeder
والاتفاق على CountrySeeder ثم بيانات مدن ومطارات وشركات ورحلات مترابطة.
لم أشغل Seeders أو أنشئ حسابات أو أمنح صلاحيات أثناء هذه المراجعة.

## الفحوص المنفذة وحدودها

- فحص الصياغة النهائي: 142 ملف PHP و61 قالب Blade بدون أخطاء، وفحص أن جميع
  أكشنات الكنترولرز المسجلة موجودة. تحقق `composer validate --no-check-publish` ناجح.
- فحص بناء Vite ناجح: 63 module. خرج البناء إلى مجلد المراجعة خارج المشروع،
  وليس إلى public/build، ولم تتغير ملفات الواجهة المصدرية بسببه.
- اختبارات آمنة بدون migrations بعد دمج الروتات: 54 اختبارًا و464 تحققًا ناجحًا.
- اختبارات دخول الأدمن ومحاولاته، ربط دخول موظف الشركة، فئات المسافرين،
  سياسات الرضّع غير المعرفة، الأدوار غير النشطة، fallback للروتات الناقصة،
  ورفض توقيع Stripe غير الصحيح. مزودا AI وStripe لم يتلقيا طلبات فعلية.
- اختبارات الربط الأخيرة تستخدم الروتات الفعلية المسجلة في web.php، بدون إضافة
  روتات بديلة داخل الاختبار. شملت تحويل الزوار وصفحات النماذج وتوقيع webhook.
- لم تُشغّل مجموعات AuthFlowTest وDev5ControllerRoutesTest وHostedStripeCheckoutTest
  وStripePaymentFlowTest وStripeRouteWiringTest وAirportControllerTest
  وContactMessageControllerTest لأنها تستخدم RefreshDatabase وتشغّل migrations.
  phpunit.xml يعزلها إلى SQLite memory، لكن حظر أوامر تغيير السكيمة ما زال قائمًا.
- لم يُختبر MySQL متزامنًا، ولم تُنفذ دفعة أو حجز أو مراجعة فعلية من المتصفح.

أمر الاختبارات المنفذة:

```powershell
php vendor/bin/phpunit tests/Feature/OmarCountriesTest.php tests/Feature/OmarDiscoveryTest.php tests/Feature/OmarMergeReviewTest.php tests/Feature/ExampleTest.php tests/Unit/ExampleTest.php
```

## ترتيب المتابعة المقترح

1. اكتمل دمج الروتات وإزالة التكرار؛ يلزم الحفاظ على هذه النسخة في دمج الفريق التالي.
2. إعداد حسابات الأدوار وبيانات المواقع والرحلات في قاعدة تطوير.
3. إكمال مسار رحلة واحد: البحث → اختيار الذهاب/العودة → draft → hold → quote.
4. حل اعتماد سكيمة الرصيد وربط الدفع والتثبيت والتذاكر قبل إعلان نجاح الحجز.
5. تشغيل اختبارات قاعدة منفصلة بعد اعتماد سياسة migrations للاختبار، ثم اختبارات
   التزامن والتكرار وعزل حسابات العملاء وملكية الرحلات.
